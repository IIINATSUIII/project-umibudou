# 問診データの統一と移行（I02 / I03 / I05 / I06）

旧手順の「AL〜AOのヘッダーだけ追記」は廃止する。#43ではALが郵便番号、#48では睡眠区分、mainでは顧客IDであり、#34は先頭付近にも列を挿入している。列番号から意味を推測しない。

## 単一定義

`src/lib/questionnaireSchema.ts` の `QUESTIONNAIRE_COLUMNS` を初期化・保存・移行の唯一の列定義とする。読み取りは実シートのヘッダー名に従う。新形式以外への追記はエラーにして、移行前の混在書き込みを止める。初期化APIは値があるシートを変更しない。

| 旧名 | 統一名 | 方針 |
|---|---|---|
| hypertension | highBloodPressure | mainと同じ高血圧項目 |
| conditionDetail | conditionDetails | 体調詳細 |
| doctorDivingPermit | doctorClearance | スタッフによる許可書確認 |
| staffCheckStatus / staffCheckNote | staffReviewStatus / staffReviewNotes | スタッフ確認状態・メモ |
| medicalCertificate | medicalCertificate | 本人申告。スタッフ確認から補完しない |

同じ意味の別名項目に異なる値があれば停止する。未知列も出力に保持する。空の睡眠時間・総本数はnull、空のbooleanは未回答。過去の心臓疾患から高血圧を推測しない。

## 手順（本番データはこのPRでは移行していない）

1. 問診提出と予約編集を停止する。元スプレッドシート全体をバックアップし、元コードのバージョンも記録する。
2. 元の**実際のヘッダーを含む全行・全列**をSheets APIのvaluesレスポンス `{ "values": [[...headers], [...row]] }` のJSONとして保存する。セルの文字列を維持する。電話・郵便番号の先頭ゼロを数値化しない。個人情報をリポジトリやPRに置かない。
3. `node scripts/migrate-questionnaires.cjs input.json` でdry-runする。重複ヘッダー、無名列、矛盾、型不正があれば停止する。すでにヘッダーだけ変更されたシートや、複数形式の行が同じヘッダー下に混在する場合は自動判別できない。バックアップ・記録から行の元スキーマを復元してから再実行する。
4. `node scripts/migrate-questionnaires.cjs input.json NEW-output.json` で新ファイルへ変換する。元ファイルは変更しない。出力が既存なら失敗する。
5. 新しいシート（例：`問診票_v2`）を必要列数以上に拡張し、出力の二次元配列を `valueInputOption: RAW` でA1から書き込む。行数・ID集合・連絡先・健康回答・QRトークン・スタッフ確認の対応をバックアップと照合する。再変換した出力が同一であることも確認する。
6. `GOOGLE_QUESTIONNAIRE_SHEET=問診票_v2` を設定してアプリを再起動。閲覧とテスト予約での保存・再取得を確認して提出を再開する。既定値は`問診票`。
7. 元シートを保存しておく。ロールバックは書き込みを止め、切替後の追加行を退避してから元コードと元シート設定に戻す。切替後の回答を失わないよう別途移行する。

ローカルJSONの配列も同じコマンドで新ファイルへ変換できる。サーバーは読み取り時に別名を正規化する。欠落値は推測で埋めない。

## 入力URLと受付QR

- スタッフ認証下の `POST /api/reservations/[id]/questionnaire-url` が `{ accessToken, expiresAt, url }` を発行。再発行は旧URLを無効化する。DELETEは入力資格を失効させる。
- 予約シートは既存11列を確認して末尾に `questionnaireToken` / `questionnaireExpiresAt` を追加する。異なる列構成・無名データがあれば停止する。
- 公開POST/GETは `accessToken` のみを受け付ける。body.token、reservationId、受付qrTokenによる代替認証はしない。期限・キャンセルを共通関数で検証する。
- 期限はダイブ日の翌日00:00 JST。予約ID形式の旧URLには新しい入力URLを発行する。期限のない旧トークンも再発行が必要。
- 受付qrTokenは送信成功時に別の乱数で発行。QRの使用済み・期限不正・期限切れは再表示不可。スタッフのID指定による過去問診の閲覧は別用途として維持する。
- キューは同一プロセス内の発行・失効・送信のみを直列化する。Sheets/JSONには複数インスタンス間のトランザクション保証はない。

## フォーム・保存契約

睡眠は `sleepCategory` を必須とし、数値に推測変換せず `sleepHours=null`。初回は `lastDivePeriod=初めて`、旧日付欄は空文字。総本数は未入力null／明示0を区別する。初回で正の総本数は拒否する。性別は`unanswered`可。体調詳細は`conditionDetails`（最大500文字）、不調時必須。写真は可否の回答を必須にし「不可」も有効。APIはゲスト入力の許可項目のみ保存する。

受付画面は高血圧、体調詳細、睡眠区分、初回・総本数未回答、本人申告の許可書とスタッフ確認を別々に表示する。

今後の関連PRは、旧ファイル全体を再適用せず、この共通スキーマ・検証・トークン契約へ合わせる。
