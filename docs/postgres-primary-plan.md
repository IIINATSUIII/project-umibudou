# PostgreSQL主保存先への移行計画

2026-10-28時点で本番運用はまだない。予約・問診・顧客・名簿・予約受付メールの主保存先をPostgreSQLとし、Google Sheetsは必要な場合だけ閲覧・集計用に同期する。ローカルJSONはDBを使わない開発用に残す。

## 1. 開発環境でPostgreSQLを起動する

`DATABASE_URL`を設定し、`npm run db:migrate`でスキーマを作成する。`db/migrations`の全ファイルが適用されたことを`schema_migrations`で確認する。`007`で始まる移行ファイルは2本あり、ファイル名全体が別のバージョンとして記録される。

## 2. 既存の開発データを確認する

SheetsまたはローカルJSONに残したいデータがある場合だけ、元データをバックアップし、`npm run db:import-legacy -- --source=sheets`または`--source=json`を実行する。このコマンドは変更せずに件数・参照・移行先の差分を調べる。予約、問診、顧客、名簿、予約受付メール、予約取消の追加項目を対象とする。問題が0件であることを確認してから、`--apply`を付けて移行する。移行中は元データへの書き込みを止める。

## 3. アプリをPostgreSQLに切り替える

`DATA_STORE=postgres`を明示してアプリを起動する。この設定では`DATABASE_URL`がない場合、別の保存先へ自動で切り替わらず起動時にエラーになる。予約の作成・更新、問診提出、顧客登録、名簿登録、受付メールの再試行を確認する。

## 4. Sheets同期の要否を決める

スタッフがSheetsを使う場合だけ、`SHEETS_SYNC_ENABLED=true`、Sheets認証情報と`CRON_SECRET`を設定し、`/api/cron/sheets-outbox`の定期実行を有効にする。`sheets_outbox`の未処理・失敗件数を確認する。同期を無効にしている間はOutboxへ追加しないため、後から有効にする場合は既存データのバックフィルが別途必要。Sheetsで直接編集した値はPostgreSQLへ戻らないため、予約などの更新はアプリで行う運用にする。

## 5. 本番公開前に確認する

本番用の空のPostgreSQLに全移行ファイルを適用し、テストとビルドを通す。保存先をPostgreSQLに固定し、バックアップ・復元手順、Sheets同期と受付メール送信のcron、監視対象を確認する。本番データの移行・削除・公開は別途確認してから実施する。
