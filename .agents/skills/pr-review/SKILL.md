# プルリクエストレビュー

PRの変更で新たに生じた不具合やリスクを見つけ、担当者が直しやすい指摘としてまとめる。レビューは読み取り専用で行い、コードやPRを変更しない。

## 対象と前提の確認

- PR URL、base/head、またはレビュー対象のブランチと作業ツリーを特定する。指定がなければ既知の upstream/default branch を調べ、実在が確認できた参照だけを使う。参照が特定できない場合は、確認可能な差分に範囲を限定し、その制約を報告する。
- `git status` と差分を確認し、コミット済みのPR差分、staged/unstaged変更、未追跡ファイルを区別する。未追跡ファイルは内容がレビュー対象に属すると確認できた場合だけ含める。
- リポジトリの `AGENTS.md`、開発ガイド、関連する設計・仕様資料を読み、今回の変更に必要なものだけ参照する。既存の変更や無関係なファイルをレビュー対象へ混ぜない。
- `.env` や認証情報ファイルの値を読んだり、出力したりしない。差分に秘密情報が含まれる疑いは、値を表示せずファイルと該当行だけ報告する。

## サブエージェントによる並行レビュー

エージェント起動が可能なら、次の3つの役割に分けて独立した読み取り専用レビューを並行して依頼する。各エージェントに対象差分、base/head、関連するプロジェクト指示を渡し、割り当てた観点に集中させる。エージェント機能が使えない場合は、同じ観点を順に確認し、その旨を記載する。

1. **動作・回帰** — 変更ロジック、呼び出し元と呼び出し先、境界条件、失敗時の動き、データ保護や認可への影響。
2. **影響範囲・一貫性** — 依存箇所、型・API・DB/データ形式・設定・文書・テストとの整合、近接コードの既存パターン。
3. **統合・競合** — 実際のbase/headと関連変更を比較し、機械的なマージコンフリクトと同じ契約・動作に対する意味上の競合を分けて確認。

各エージェントには、変更された行を含む正確なファイル・行、問題が起きる条件、具体的な影響、最小の修正案を求める。スタイルの好み、根拠のない推測、変更と無関係な既存問題は指摘候補にしない。メインレビュー担当は各候補をソースと周辺文脈で再確認し、重複と誤検出を除く。

## 確認の進め方

- 変更の意図と差分範囲を把握し、変更行を起点に関連コード・呼び出し元・データの流れを追う。
- 動作の正しさ、エラー処理、境界条件、認証・認可、入力検証、データ損失や重複、並行更新、互換性を変更に応じて確認する。
- 影響範囲を呼び出し先や利用画面までたどる。型・API・DB/データ形式・環境設定を変える場合は、利用箇所や移行手順、仕様書、README、テストとのずれを確認する。
- 既存実装との一貫性は、同じ機能や近い責務のコードと比較して判断する。単なる書き方の違いは、不具合や保守上の具体的な危険につながらない限り指摘しない。
- 既存CIやテスト結果が確認できる場合は、その事実と範囲を記載する。実行していない検証を通過したように書かず、ユーザーや上位指示が求めていないテストを勝手に追加・実行しない。
- コンフリクト確認は、base/headの実在する参照を使って行う。機械的な確認ではマージ結果を読み取り専用で調べ、実際に比較していない場合は「未確認」と明記する。重複行や同一ファイルの変更だけからコンフリクトなしと結論づけない。マージ、リベース、チェリーピックはしない。
- プロジェクト固有の注意事項がある場合は、該当変更に関係する範囲で確認する。このリポジトリでは `CLAUDE.md` と関連する `docs/` を参照し、Google Sheets へのサーバーサイド限定アクセス、秘密情報、認証対象ルート、ランダムな問診票ID、環境変数の文書化、個人・健康情報の保護を特に確認する。

## 指摘の基準と形式

指摘は変更によって生じた、具体的に再現・説明できる問題に限る。問題が確認できた変更行を示し、優先度順に次の形式で列挙する。

```text
P1 — [短い問題の見出し]
場所: path/to/file.ext:行
問題と影響: [問題が起きる条件とユーザー・システムへの具体的な影響]
修正案: [編集箇所が分かる最小の修正]
確認方法: [必要な場合のみ]
```

- **P1**: リリースや主要フローを止める、重大なデータ・セキュリティ上の問題。
- **P2**: 通常の使い方で起きる可能性が高い不具合、または重要な機能の欠落。
- **P3**: 限定条件で起きる低影響の不具合。好みや純粋なnitは含めない。

## レビュー結果のまとめ

日本語で、まず指摘を重要度順に示す。続けて、問題がなければ「確認範囲内で指摘なし」と明記し、レビューした差分、CI/テストの確認状況、コンフリクト確認の対象参照と結果、未確認事項を短くまとめる。指摘なしは不具合が存在しない保証として扱わず、確認できた範囲を明示する。
